# ADR-012：`.kib` 备份的合并导入范围

- 状态：已接受
- 日期：2026-10-20
- 影响范围：`src/core/vault/backup.ts`、`src/services/vault-client.ts`、设置面板

## 背景

SDD §9.2 要求恢复支持「覆盖」与「合并」两种策略：覆盖是二次确认后的事务替换；
合并要求「按 item id 不直接覆盖；同标题/同 URL 冲突时展示冲突列表」。

备份 payload 里保存的是**源库的密文资产记录**，这些密文是用源库 DEK 加密的。

## 决策

1. **覆盖导入**：事务式写入密钥槽、元数据、资产与最近使用；任一步失败按逆序回滚
   （密钥槽最后写回，它是「库还能不能被打开」的最终保证），失败报 `STORAGE_FAILED`。
   导入成功后会话回到锁定态，用户需用源库主密码解锁。
2. **合并导入**要求备份与当前库**同 DEK 世系**（两侧密钥槽记录的
   `wrappedDek / salt / nonce / version` 逐字节相同）：
   - 世系相同 → 密文可被当前会话解开，按明文内容比较：
     完全一致跳过、同站点不同凭据记为冲突并保留当前版本、缺失资产按新 id 插入。
   - 世系不同 → 拒绝合并，提示改用覆盖导入。否则只会往库里塞入当前 DEK
     无法解密的「坏卡片」，用户会看到乱码密码且无法察觉。
3. **明文比较而非密文比较**：本项目每次写操作都会为整表重新生成 nonce，
   同一份明文两次落盘的密文必然不同，因此「相同内容」必须解密后按业务字段判断。

## 后果

- 合并导入的安全语义清晰：要么真的能解密并按内容去重，要么明确拒绝。
- 代价是跨库备份只能整体覆盖，不能增量合并；这是密文 DEK 世系决定的，
  在 DEK 移入 Rust 之前不存在更安全的实现（要跨库合并必须先把备份内容
  用源 DEK 解密再逐字段重加密，需要源库主密码，超出备份密码的语义）。
- 后续若接入真实文件系统，`.kib` 的读写端口需保持同样约束。
