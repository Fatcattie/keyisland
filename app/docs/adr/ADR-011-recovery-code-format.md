# ADR-011：恢复码编码格式与"32 位"约束的落地方式

- 状态：已接受
- 日期：2026-10-20
- 相关文档：SDD §4.1、§15 ADR-007；PRD FR-08

## 背景

PRD / SDD 对恢复凭据有两处看似冲突的要求：

1. 恢复码是"32 位分组字符，可抄写打印"（PRD FR-08），SDD 建议 4 组 8 位或 8 组 4 位。
2. 恢复密钥（KEK-B 的派生输入）按 32 字节处理，与 DEK 长度规格一致。

32 字节 = 256 bit，用 Base32（5 bit/字符）编码需要 52 个字符，与"32 位"直接矛盾。

## 决策

- 恢复码承载 **20 字节（160 bit）** 的随机秘密，编码为 **32 个 Crockford Base32 字符**，按 8 组 4 位展示（`XXXX-XXXX-...`）。
- 恢复密钥 = `SHA-256(20 字节秘密)`，得到 32 字节，作为 Argon2id 的输入派生 KEK-B。
- 因此恢复码与 `.kirk` 文件内容**完全等价**：都能得到同一个 32 字节恢复密钥。
- `.kirk` 只保存恢复密钥（Base64）、`magic: KIRK1`、`version: 1`、`createdAt` 与可选 `label`，**不含主密码、不含恢复码原文**。
- 校验策略：
  - 归一化：大写化、去空格/连字符、Crockford 混淆字符修正（`O→0`、`I/L→1`、`U→V`）；
  - 格式校验：长度必须为 32、字符必须在字母表内；
  - 密码学校验：格式合法但内容错误的恢复码，会在 AES-GCM 解包 KEK-B 时被认证标签拒绝，等价于强校验和。

## 理由

- 160 bit 熵远超暴力破解可行域，且比 128 bit 更宽裕；同时满足"32 位可抄写"的产品要求。
- 用 SHA-256 扩展而不是截断 256 bit 秘密，可以保证恢复密钥长度与 DEK/KEK 规格统一（32 字节），不引入额外长度分支。
- Crockford Base32 去掉 `I / L / O / U`，显著降低手抄错误率；同时保留 `0/1` 与 `O/I/L` 的纠正映射。

## 后果

- 恢复码不能直接当作 32 字节密钥使用，必须经过 `recoveryKeyFromCode()`。
- Phase 1.5 Rust 实现必须保持同一编码与同一 `SHA-256` 扩展步骤，否则旧 `.kirk` 文件失效。
- 若未来要加"校验位"，必须升级 `KIRK1 → KIRK2` 并保留旧版本解析分支，不能在现有格式上追加字符。
- **恢复密钥本身不持久化**：`keyslots.recovery` 只存用 KEK-B 包住的 DEK；恢复密钥是 Argon2id 的输入，
  用完即 `zeroize`。所以"把当初那个 `.kirk` 再导一次"在密码学上不可行——库里没有任何地方能取回它。

## 补充决策（2026-10-30）：`.kirk` 丢失后怎么办

需求是"要有重新导出 `.kirk` 的能力"。在不改动上面的前提下，只有一条路能走：

- 新增 `exportRecoveryKirk(recoveryCode)`：用**恢复码**重新派生同一把恢复密钥并写出 `.kirk`。
  它**不写存储、不动密钥槽、不让旧码失效**——与"重新生成恢复密钥"（轮换）是两条完全不同的路径，
  界面上也必须分开表述，否则用户会以为自己又换了一次钥匙。
- 先验证后出文件：解不开 B 槽的码一律不产出文件，避免发一把"看着像钥匙"的废纸。
  校验复用 `session.recover()`，与解锁页共用失败计数与冷却期，不留"在设置里无限次猜码"的旁路。
- **不接受**"把恢复密钥（或那 20 字节秘密）加密存进库"来换取一个无条件可点的导出按钮：
  那会让恢复密钥从"只在你手上"变成"库里也有一份"，把一条独立于主密码的找回通道
  降级成主密码的附属物。代价是连恢复码也丢了的人只能轮换一把新的（旧码作废）。
