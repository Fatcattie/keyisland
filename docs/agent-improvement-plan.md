## 3. 任务 1：将整库替换改为数据库原子事务（高优先级）

### 已确认的问题

`app/src/services/vault-client.ts` 的 `internalImportBackup()` 覆盖分支（约 1921 行）依次保存 `keyslots`、`meta`、`items`、`recency`。异常时尝试通过反向写入恢复旧数据。

`app/src/services/tauri-storage.ts` 每次保存独立调用 `storage_save`；`app/src-tauri/src/storage.rs` 的 `Store::set()` 每次单独执行一条更新，没有跨上述四次调用的事务。

捕获异常后的补偿写入无法覆盖断电、进程被终止等情况，也可能再次遇到磁盘故障。若在新密钥槽写入后中断，旧资产可能与新密钥槽不匹配，导致库无法正常解锁或解密。

### 修复要求

- 为整库初始化、备份覆盖等多键写入提供明确的原子存储操作，由 Rust 在同一 SQLite 事务中完成。
- 更新 `VaultStorage`、内存实现、Tauri 实现、IPC 注册以及相应测试替身，使原子语义一致。
- 事务提交成功后再切换会话及内存状态；失败时旧库与旧会话应保持一致。
- 不把多个独立 IPC 调用套进前端 `try/catch` 当作数据库事务。
- 检查恢复、初始化等其他多键写入路径，记录哪些需要采用同一接口及理由。

### 验收标准

- 正常覆盖后，重启可用备份对应的认证材料解锁，资产与元数据完整。
- 在各写入阶段注入错误后，重新打开数据库仍得到完整旧库，不出现混合状态。
- 用隔离测试验证事务未提交时连接关闭或进程中断，重启后保留旧库；提交后保留完整新库。
- 提供 Rust 层真实 SQLite 事务测试，不能只依赖模拟 IPC。
- 原有初始化回滚、恢复、迁移、备份及存储契约测试通过。

## 4. 任务 2：正确处理剪贴板清理失败（高优先级）

### 已确认的问题

`app/src/services/clipboard.ts`：

- `BrowserClipboardPort.clear()` 吞掉 `writeText('')` 的异常。
- `ClipboardService.tryClear()` 也吞掉端口异常。
- `handleExpiry()` 随后仍记录 `cleared` / `cleared-unverified`，并调用 `onCleared`。

因此清理失败可能被报告为成功。默认客户端在桌面端也使用浏览器剪贴板端口，需验证真实 WebView 失焦后的读写行为。

### 修复要求

- 让清理结果可观测，明确区分成功、无法验证归属、已被用户覆盖、清理失败。
- 仅在清理确实成功后发出成功事件；处理锁定和退出路径中的失败语义。
- 失败时给出适当提示，并设计有界重试或其他明确处置，避免无限定时器及未处理异常。
- 保留内容摘要归属判断，不在任务或日志中长期保存密码明文。
- 评估桌面端原生剪贴板适配器；若引入，明确权限、读取失败策略及与浏览器预览的差异。
- 重试期间若内容已被用户覆盖，不应按旧任务清掉新内容；处理多次快速复制的竞态。

### 验收标准

- 端口清理抛错时不会产生“已清理”的事件或结果。
- 成功清理、读权限失败、写权限失败、用户覆盖、连续复制、锁定和退出均有针对性测试。
- 重试有上限，结束后没有泄漏的定时器或未处理 Promise rejection。
- 在 Windows 桌面版验证失焦、缩成岛、锁定后的行为；没有运行环境时明确列为未验证。

## 6. 任务 4：限制导入资源消耗（中优先级）

### 已确认的问题

`app/src/features/settings/SettingsPanel.tsx` 的 `handlePickAssetBundle()`、`handlePickFile()`、`handleCsvFile()`（约 1050 行起）直接通过 `file.text()` 或 `FileReader.readAsText()` 读取整个文件，读取前没有文件大小限制。

备份与迁移包解码器使用 JSON 解析和 Base64 解码。超大文件可能产生多份内存副本；加上解密与解析，可能导致界面卡顿或内存耗尽。具体容量阈值需结合产品容量目标确定，不能凭空宣称当前会在某一规模崩溃。

### 修复要求

- 集中定义文件字节数、条目数、字段长度等合理上限，并说明依据和用户文案。
- 文件选择在读取前检查 `file.size`；粘贴输入和领域解码入口也必须有上限，避免绕过 UI。
- 在大额分配、Base64 解码和 KDF 派生前校验能提前校验的结构及长度。
- 检查已有 Argon2 参数边界，评估是否允许过大的资源预算；保持合法旧格式兼容，说明取舍。
- 根据目标规模决定是否需要 Worker、进度与取消；避免仅加进度动画却仍阻塞主线程。
- 拒绝导入时不修改当前库，不在错误提示中回显密码或资产内容。

### 验收标准

- 覆盖限制以内、恰好边界、超过边界、损坏文件及粘贴绕过路径。
- 过大文件在读取前被拒绝；过大文本在昂贵解析或解密前被拒绝。
- 拒绝后当前资产、密钥槽和元数据保持原样，界面仍可继续操作。
- 文档说明支持的容量范围及限制。

## 7. 任务 5：将资产保存改为增量更新（中优先级）

### 已确认的问题

`app/src/core/vault/items.ts` 的 `ItemService.flush()`（约 492 行）遍历全部内存资产，逐个重新加密后调用 `saveItems(records)`。因此修改单张卡片也会重新加密和整体写入全部资产。当前尚未取得千条、万条数据的耗时基线。

### 修复要求

- 使用合成数据记录 100、1000、10000 条资产下的新增、编辑、删除、批量导入耗时，作为前后对照。
- 设计按资产 ID 的增量写入与删除接口，批量操作采用事务；与任务 1 的原子整库替换协调。
- 保持标题、平台、标签等资产元数据的落盘保密性，不能为了 SQL 查询或索引将其变为明文。
- 若调整密文 AAD，绑定稳定的记录身份并提供旧格式迁移；保留随机 nonce 和认证校验。
- 提供旧 `items` 聚合记录向新结构迁移的原子方案，失败后旧库仍可读取。
- 检查并发保存、保存失败后的内存一致性、锁定期间在途写入，以及备份与恢复格式兼容。

### 验收标准

- 单卡修改不会重新加密和写入无关卡片；使用调用计数或记录对照证明。
- 批量操作不会部分提交，并发修改不会静默丢失。
- 旧库迁移、迁移失败恢复、备份覆盖与合并、CSV 和 `.kia` 导入均正常。
- 提供可复现的性能对照；性能改善不能以减少加密或认证保护为代价。
